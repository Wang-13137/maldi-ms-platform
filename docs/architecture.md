# 数据与评测中台的分层设计

这份文档说明每个决策**为什么这么做**，实现细节看代码。

## 一、为什么是"中台"而不是"一个脚本"

三个项目原本各自有一份评测脚本：

- `maldi-ms-pipeline`：16 项测试，验证的是**算法正确性**（峰检测、归一化、特征筛选）；
- `maldi-ms-agent`：64 条扰动实测 + 10 条行为门禁，验证的是**Agent 行为**（会不会虚报）；
- `medical-rag`：206 项测试 + 检索指标，验证的是**检索质量**。

问题是这三套东西的**结果没法互相比较**：指标名不同、样本口径不同、"这版比上版好"
没有任何统一判据。更麻烦的是数据侧——同一个 37 例数据集在不同脚本里有三套特征矩阵，
没人能确认哪份对应哪个结论。

中台要解决的就是这两件事：**数据的身份**（哪份数据）和**结论的判据**（好还是坏，显著吗）。

## 二、分层

```
┌─────────────────────────────────────────────┐
│  CLI（maldi-platform）  ·  静态看板（HTML）   │  ← 人看的部分
├─────────────────────────────────────────────┤
│  评测中台 evals.py      数据中台 datasets.py  │  ← 业务规则
│  ├ 套件 / 运行 / 指标    ├ 数据集 / 版本      │
│  ├ 配对比较 / 门禁       ├ 字段 / 切分        │
│  └ 血缘                  └ 导出门禁 / 哈希    │
├─────────────────────────────────────────────┤
│  stats.py（Wilson / McNemar）                │  ← 统计原语
├─────────────────────────────────────────────┤
│  db.py（SQLite，9 张表，schema v1）           │  ← 存储
└─────────────────────────────────────────────┘
```

没有 Web 层。理由：单用户、三个项目、离线环境，一个 CLI 加快照页的运维成本接近于零，
而一个带鉴权的服务会引入部署、备份、升级三件长期负担。等真的多人协作了再说。

## 三、数据中台的关键取舍

### 只存元数据，不存数据

`dataset_versions.storage_path` 是一个**指针**。中台从头到尾不读数据内容（除了算哈希），
也不复制。好处有三：

1. 真实数据不可能因为"用了中台"而扩散；
2. 数据更新不会让中台变成第二份真相；
3. 库文件很小（几十 KB），能随便拷、能进备份。

代价是"数据搬家了中台不知道"。这个代价可以接受——哈希才是身份，路径只是线索。

### 哈希算法

```
content_hash = sha256( json( sorted([{path, sha256, size}, ...]) ) )
```

排序保证顺序无关，相对路径保证目录可搬，逐文件哈希保证内容敏感。
测试里直接断言"copy 到另一个目录 → 哈希相同"和"改一个字节 → 哈希不同"。

### 导出策略是硬编码的两层

| 分类 | metadata | payload |
|---|---|---|
| synthetic + open | ✅ | ✅ |
| synthetic + internal | ✅ | ❌ |
| synthetic + restricted | ✅ | ❌ |
| **real（任意策略）** | ✅ | **❌ 硬拒** |

`real + open` 在**登记阶段**就报错，而不是等到导出时。因为一个"配置成 open 就能导出"的
系统，最终一定有人配置成 open。

## 四、评测中台的关键取舍

### 配对比较，不是比率比较

同一次评测的不同臂共享同一批样本（同 case_id）。正确做法是按 case 配对：

```
        候选通过   候选未过
基线通过    both      a_only
基线未过    b_only    neither
```

McNemar 精确检验只看 `a_only / b_only`：`p = 2·P(X ≤ min(a_only, b_only))`，`X ~ Bin(n, 0.5)`。

为什么必须精确：`a_only=11, b_only=0` 时精确 `p = 2/2^11 ≈ 0.000977`，卡方近似会给出更小的值。
样本只有 16 条时，近似不可信。

### 门禁分三类，各管一件事

| 门禁 | 判据 | 防的是什么 |
|---|---|---|
| `min_pass_rate` | 通过率 ≥ 阈值 | 整体崩掉 |
| `no_regression` | 相对基线**不显著变差** | 静默退化 |
| `require_<metric>` | 过程指标 ≥ 阈值（如置换检验调用率） | 步骤被跳过但结果看着还行 |

`no_regression` 故意宽松：只在显著变差时拦。n=16 时少过 1 条就是 6.25% 的"下降"，
按固定百分比拦会天天误报，最后没人看门禁。

### 指标由 cases 重算，不由输入方自报

`_refresh_metrics` 从 `cases` 表重新统计，不信任 payload 里给的 `rate`。
输入方可以给错，但中台算出来的必须是自洽的——这样"11/16"和"68.8%"永远不会打架。

### 三种报告格式，一个原则：只吃逐题明细

| 来源 | 识别标志 | 入几个 run | 通过判据 |
|---|---|---|---|
| 平台原生 | `cases[]` | 1 | 自带的 `passed` |
| `maldi-ms-agent` | `runs[]` | 每个消融臂 1 个 | `grade.correct` |
| `medical-rag` | `answerable_per_query[]` | 1 | `full_coverage == 1`（全中） |

`generation_compare_*.json` 这类只有聚合结论（`left/right/n_pairs/scopes`）的报告
**直接拒收**。这不是偷懒：没有逐题明细就没法重算，也就没法配对，收进来等于替对方
的统计口径背书——而"不信任自报数字"正是这个中台存在的理由。

拒答题的处理单独说，因为它最容易做错。`medical-rag` 的报告给了 15 条应拒答题，
同时给了一个 `refusal_tradeoff.best.threshold`。这个阈值是用**同一批数据**按
Youden J 挑出来的最优值，而且逐臂不同。拿它给自己的拒答打分是循环论证，跨臂比较
还会把"检索质量"和"阈值调参"混成一个差值。所以：

- 默认**不计入通过率**，只记 `unanswerable_top1_mean` 作观测；
- `--include-unanswerable` 可显式纳入，此时按"检索不到 gold 即未通过"计入；
- 无论哪种，理由都写进 `runs.config.note`，跟着数据走，不靠文档口头传承。

## 五、看板为什么是静态 HTML


需求是"发给人看、能进仓库、能离线打开"。任何前端框架都不满足"离线打开还能没有构建步骤"。
所以看板是服务端拼字符串：内联 CSS、内联 SVG 条、零 JS、零外链。
测试里直接断言 `http://`、`https://`、`<script` 都不出现，防止哪天顺手引了个 CDN。

## 六、血缘

```
dataset_version --consumed_by--> run
```

只记这一条边，但它回答了最要命的问题："这个 11/16 是哪份数据跑出来的"。
当数据从 37 例扩到 150 例、从 1 个批次变成 3 个批次时，没有这条边就只能靠回忆。

## 七、没做的与原因

| 没做 | 原因 |
|---|---|
| Web API / 鉴权 / 多租户 | 单用户场景，收益低于运维成本 |
| 实验调度 | 评测在项目侧重跑，中台只管结果的可信记录 |
| 前端交互 | 静态页已够看；交互会引入构建链 |
| 特征存储 | 特征由 pipeline 产出，中台只登记字段元数据 |
| 自动拉模型 API | 外部调用意味着数据可能出域，与红线冲突 |
