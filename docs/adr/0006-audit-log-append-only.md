# ADR-0006：审计日志只追加，并用触发器钉在库层

- 状态：已采纳
- 日期：2026-11-05

## 背景

中台要回答的问题之一是"谁在什么时候把哪份数据导出去了"。这既是内部追溯需求，
也是医疗数据合规的常见要求。只写应用层日志（打印到 stdout）不够：日志文件可以被
删、被截断、被覆盖，而"日志丢了"和"没发生过"在事后无法区分。

## 决策

建 `audit_log` 表，记录 `ts / actor / action / target / outcome / detail`，并且：

1. **不提供任何修改或删除的 API**；
2. **在库层用 `BEFORE UPDATE` / `BEFORE DELETE` 触发器 `RAISE(ABORT)`**，绕过 API 直接写 SQL 也不行；
3. **写入失败即业务失败**：审计写不进去说明库有问题，此时操作不能算成功。

## 理由

- "只追加"如果只靠代码自觉，一次临时排查就能用 `UPDATE` 改掉，审计的意义就没了；
  触发器把约束放在数据层，改它需要显式 `DROP TRIGGER`，是明确的越界动作；
- 记录"被拒绝"的导出比记录"成功"的更重要——异常往往发生在被拒的那一侧；
- 不记录数据内容，只记录标识与结论，避免审计表自己变成新的泄露面。

## 代价

- 表会一直增长，没有自动归档。当前量级（每次操作一行）几年内都不构成问题；
- 触发器让"批量清理测试库"变麻烦——需要先 `DROP TRIGGER`，这正好是设计意图；
- `actor` 只是记录，不是认证。单机工具无法验证身份，生产部署应由上层注入（SSO / 网关）。

## 否决的方案

- **写文件日志**：可删可改，与库不在同一个事务里，无法保证"操作成功则日志存在"；
- **应用层加 `audit_no_update` 开关**：开关本身就是绕过路径；
- **只记成功动作**：会漏掉最重要的一类事件（试图导出被策略拒绝的数据）。
