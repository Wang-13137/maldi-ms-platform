# ADR-0002：用单个 SQLite 文件承载全部状态

- 状态：已采纳
- 日期：2026-11-04

## 背景

评测中台要存的数据量很小：几十个数据集版本、几百个 run、每个 run 几十到几百条逐题结果。
使用方是单人或小团队，跑在笔记本与 CI 上，经常没有网络。

## 决策

全部状态放在一个 SQLite 文件里，不引入数据库服务，也不引入 ORM。

## 理由

- **可携带**：一个文件就是全部状态。发给合作者、放进 U 盘、在 CI 里当 artifact 上传都是复制文件；
- **可审计**：`sqlite3 platform.db .dump` 就能看到全部内容，不需要连服务、不需要凭据；
- **零依赖**：`sqlite3` 在标准库里。这条约束让整个项目保持"解压即用"，也让离线环境能用；
- **够用**：写入是单进程、低并发，SQLite 的写锁完全不是瓶颈。真正的瓶颈在人对结论的解读，
  不在 QPS。

## 代价

- 没有并发写：两个人同时往一个库写会有一个等锁。当前场景（本地 + CI 各用各的库）可接受；
- 没有网络访问：做不了"多人共享一个中台"。真需要时应该部署服务，而不是把 SQLite 放到共享盘上
  ——后者会在网络文件系统上丢锁；
- 备份靠复制文件，没有 PITR。中台的数据可以由源报告重放重建，RPO 要求不高。

## 否决的方案

- **PostgreSQL**：需要部署、需要凭据、CI 里要起服务。为了几百行数据付出这些成本不划算；
- **DuckDB**：分析性能更好，但当时对 Python 3.10 的轮子覆盖不如 SQLite 稳，
  且它不是标准库，会破坏"零依赖"这条约束；
- **JSON 文件当存储**：没有事务、没有唯一约束。重名覆盖、半写坏文件这两个问题会直接
  破坏"版本不可变"的语义。
