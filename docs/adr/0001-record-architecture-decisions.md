# ADR-0001：用 ADR 记录架构决策

- 状态：已采纳
- 日期：2026-11-04

## 背景

这个项目里多数决策都不是"怎么写代码"，而是"该信哪个数字"：指标要不要自己重算、
拒答题算不算通过、门禁按百分比还是按显著性拦。这些决策一旦只在提交信息里，
半年后没人说得清为什么，下一个人就会"顺手改成看起来更合理的样子"，
然后把一个好不容易校准过的口径推翻。

## 决策

用 Architecture Decision Record 记录关键取舍，放在 `docs/adr/`，一篇一个决策，
包含：背景、决策、理由、代价、**否决的方案**。

## 理由

- 代码说明"是什么"，ADR 说明"为什么不是另一种"——后者才是评审与交接时被问到的部分；
- 否决方案比结论更有信息量：它防止下一个人重新提一个已经被否掉的方案；
- 写在仓库里而不是文档系统里，跟代码一起评审、一起版本化，不会脱节。

## 代价

写一篇要多花十几分钟；如果团队不读，就退化成形式主义。缓解办法是只在
"改了会有人质疑"的地方写，目前 6 篇，覆盖存储选型、版本定义、指标口径、审计策略。

## 否决的方案

- **只在 PR 描述里写**：PR 会被合并进历史，但不会被检索；新人不会去翻 200 个 PR。
- **写在 Wiki**：与代码分离，改代码时不会同步改 Wiki，半年后必然出现两份互相矛盾的说明。
