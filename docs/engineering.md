# 工程规范

这份文档回答一个问题：**这个仓库凭什么是"工程"而不是"脚本集合"**。
每一条都能在 CI 或代码里指到具体实现，不是口号。

## 一、质量门禁（四道，全在 CI）

| 门禁 | 工具 | 阈值 | 失败后果 |
|---|---|---|---|
| 静态检查 | ruff（E/F/W/I/N/UP/B/C4/SIM/RUF） | 0 告警 | PR 不能合并 |
| 格式 | ruff format | 无差异 | PR 不能合并 |
| 类型 | mypy（`warn_return_any`、`strict_equality`、`check_untyped_defs`） | 0 错误 | PR 不能合并 |
| 测试 + 覆盖率 | pytest + coverage（**分支覆盖**） | 111 项全过、≥ 85% | PR 不能合并 |
| 命令行冒烟 | 真实跑一遍 CLI | 退出码全对 | PR 不能合并 |

冒烟那一步不是"再跑一次测试"，而是**从使用者视角验证契约**：比较必须报显著、门禁失败
必须返回 1、真实数据 payload 必须导不出、只有聚合结论的报告必须被拒收。这四条一旦漂移，
单元测试全绿也没有意义。

覆盖率当前 90.2%（分支）。阈值定 85% 而不是贴着 90%：贴着实测值会让每个无关 PR 都要
补测试才能过，最后大家学会的是"调低阈值"而不是"写测试"。

## 二、CI 矩阵

- **三平台矩阵**：Python 3.10 / 3.11 / 3.12（3.10 是声明的最低版本，必须真测，
  不能只写在 `requires-python` 里）。
- **额外一个 job**：命令行冒烟 + 看板生成 + 门禁退出码，固定跑 3.12。
- 全部 `ubuntu-latest`，无缓存依赖，安装时间即真实冷启动时间。

## 三、版本与 schema 两条线

包版本（`pyproject.toml`）与数据库 schema 版本（`db.SCHEMA_VERSION`）**独立演进**：

- 包版本走语义化版本：加功能升次版本，改指标口径或命令行为升主版本（0.x 阶段按次版本处理）；
- schema 版本只在表结构变化时 +1，迁移脚本**只增不改**——已发布的迁移脚本进入使用者
  手里后就不能再动，否则同一个库在不同机器上会演化成两种结构；
- `init` 自动往前迁移；库比程序新时**拒绝启动**（退出码 3）。不做静默降级：
  用旧程序写新库是最难发现的数据损坏。

0.2.0 的 v1 → v2 迁移新增审计表，历史数据零改动，已在真实的 64 条评测库上验证过。

## 四、发布流程

1. 更新 `CHANGELOG.md`（`Added` / `Changed` / `Fixed` / `Schema` 四类）；
2. 改 `pyproject.toml` 与 `__init__.py` 两处版本号（CI 不断言两者一致，靠评审卡）；
3. 打标签 `v0.2.0` 并推送；
4. `release.yml` 构建 sdist + wheel，`twine check` 校验元数据，产物附到 Release。

发布产物是**可复现**的：运行时零第三方依赖，`python -m build` 在任何机器上都能重放出包。

## 五、目录职责

```
src/maldi_platform/
  db.py         连接、建表、schema 版本与迁移（唯一知道表结构的地方）
  datasets.py   数据中台：登记、内容哈希、导出门禁、血缘
  evals.py      评测中台：入库适配、指标重算、配对检验、门禁判据
  stats.py      纯函数统计（Wilson 区间、McNemar 精确检验）——无 IO，最好测
  report.py     静态看板渲染
  audit.py      追加型审计日志
  cli.py        参数解析与输出格式（唯一对用户负责的层）
tests/          按模块对齐，helpers.py 放报告构造器
docs/adr/       架构决策记录：为什么这样做，以及否决了哪些方案
```

分层的硬规则：**业务层不打印，CLI 层不算数**。`evals.py` 不出现 `print`，`cli.py` 不出现
统计公式。这样换输出格式（JSON / HTML / 未来的 HTTP）不需要动业务逻辑。

## 六、错误处理约定

| 情况 | 行为 | 退出码 |
|---|---|---|
| 业务错误（重名、版本冲突、报告格式不对） | 抛 `DataError` / `EvalError`，CLI 打印后退出 | 1 |
| 导出被策略拒绝 | 抛 `ExportDeniedError`，同时写审计 | 1 |
| 门禁未通过 | 打印每条结论，不抛异常 | 1 |
| schema 不兼容 | 抛 `SchemaError` | 3 |
| 参数错误 | argparse 自己处理 | 2 |
| 审计写入失败 | 抛 `AuditError`，业务操作失败 | 1 |

不用 `sys.exit()` 散落在业务层；`main()` 是唯一出口，测试可以直接断言返回码。

## 七、非目标

写清"不做什么"比写"做了什么"更能说明设计意图：

- 不做 Web 服务与多用户权限——这一版是单机工具，身份与访问控制交给部署层；
- 不做数据存储与迁移——只登记指针与哈希，数据本体留在受控存储里；
- 不做模型训练与推理——中台只判"结论站不站得住"，不产生结论；
- 不做可视化大屏——看板是自包含 HTML，目的是"能贴进汇报、能离线打开"，不是 BI。
